# Design Specificity Verdict

**结论：产品语义明确，但主要构图仍偏通用 SaaS 管理台。**

ShareSub 的珊瑚、青绿、蓝色语义体系，以及 Plan、额度窗口、成员份额、账号绑定和 Key 路由等对象明显来自真实业务。`frontend/src/components/OnboardingGuide.vue` 对房主与成员路径的分流尤其具有产品特异性。

但固定侧栏、数量加 CTA 的工具栏、白色小圆角卡片、图标底板、分段标签页和定义列表，仍可无痛套到其他基础设施产品。最大机会不是增加装饰，而是把“独立身份通过共享 Codex 账号协作”表达成一套一眼可读的关系结构。

**Deterministic scan:** `detect.mjs --json frontend/src` 返回 `[]`，退出码 0，共 0 条规则命中，无误报。检测器没有捕获人工评审提出的系统性体验问题，这些问题属于信息架构、认知负担和跨页面关系表达，不是静态反模式。

**Visual overlays:** 首页 `/` 在全新浏览器标签页成功加载，但可变注入预检阻塞后被中止；没有可靠的用户可见覆盖层，也没有注入后的控制台检测结果。

# Overall Impression

这是一个语义纪律和高风险操作设计明显高于普通后台的产品，但“清晰协作台”的承诺尚未完全落到结构层面。用户能看到资源，却仍需自行拼接 Account、Plan、成员与 Key 的依赖关系。最值得投入的方向是把资源管理界面升级为协作健康与就绪状态界面。

# What's Working

1. **引导贴合真实业务模型。** 它按房主/成员意图区分路径，并根据账号、Plan、邀请和 Key 状态给出下一步，而非泛泛介绍功能。
2. **高风险动作使用了恰当摩擦。** 撤销、移除成员、转移所有权、归档和永久删除均有与影响相称的确认。
3. **设计系统语义稳定。** 浅色和深色主题共享一致的珊瑚、青绿、蓝、琥珀、红色含义，响应式也不是简单缩小桌面布局。

# Priority Issues

## [P1] 操作界面的字体过小

**Why it matters:** 卡片、表格、通知、配额与弹窗中大量使用 10–11px 文本，和文档中的 13px body 令牌不一致。数据密集任务需要比较额度、身份、路由和状态，小字号会增加疲劳并伤害低视力用户。

**Fix:** 正文最低 13px，次级元数据最低 12px；10–11px 仅保留给短 micro label。同步增加多行元数据的行高和表格行高，再重新验证密度。

**Evidence:** `frontend/src/style.css:223`、`frontend/src/featureStyles.css:104`、`frontend/src/views/AdminView.vue:128`。

**Suggested command:** `$impeccable typeset`

## [P1] 信息架构按资源分类，而非按用户目标组织

**Why it matters:** Dashboard、Lobby、Plans、Accounts、Keys、Profile、Admin 均作为同级入口。完成“让团队可以使用 Codex”需要跨多个页面并记住依赖关系，与“边界清楚”的产品承诺冲突。

**Fix:** 在 Dashboard 和 Plan Overview 增加 Account → Plan → Members → Key/路由 的就绪链或关系图；阻塞状态直接链接到修复入口。桌面端可把 Accounts 与 Keys 归入“连接与访问”。

**Evidence:** `frontend/src/App.vue:206`。

**Suggested command:** `$impeccable shape`

## [P1] Plan 详情同时承载过多同级模式和高风险控制

**Why it matters:** Overview、Account、Members、Activity、Settings 五个同级标签页，加上密集头部与多类提醒，超过四项工作记忆建议。Settings 又混合常规编辑、公开设置、绑定、转让、归档和删除。

**Fix:** 让 Overview 成为真正的 Plan 控制中心，优先呈现就绪状态和异常；保留 Members、Activity 为主要模式，将 Account 收进 Connection 区域，把转让、归档和删除隔离进 Lifecycle & ownership。

**Evidence:** `frontend/src/views/PlansView.vue:20`。

**Suggested command:** `$impeccable distill`

## [P2] 禁用状态和技术指标缺少可达解释

**Why it matters:** 仅靠 hover `title` 解释禁用动作不适用于触屏和键盘用户；RPM、TPM、TTFT、CCS 等指标没有说明其对用户决策的影响。

**Fix:** 在禁用主操作旁显示可见原因与修复链接；为术语提供短定义，优先解释“这会影响什么”。

**Evidence:** `frontend/src/views/KeysView.vue:35`、`frontend/src/views/DashboardView.vue:38`。

**Suggested command:** `$impeccable clarify`

## [P2] 错误恢复过度依赖全局通知

**Why it matters:** 全局 toast 会消失，也不能指明具体字段或对象；复杂表单若只能刷新，会打断任务并可能丢失上下文。

**Fix:** 在出错表单或区块就地呈现可操作错误，保留已输入值并提供定向重试；异步视图优先重试组件加载，而非整页刷新。

**Evidence:** `frontend/src/views/AccountsView.vue:161`、`frontend/src/components/APIKeySetupWizard.vue:127`、`frontend/src/components/AsyncViewError.vue:5`。

**Suggested command:** `$impeccable harden`

# Persona Red Flags

## Alex（高频管理者）

- 缺少键盘快捷键、命令面板、保存筛选和批量操作。
- 诊断 Plan 是否可路由需要跨五个标签页及多个资源页面。
- 成员、申请、用户、账号与 Key 基本只能逐项维护。

## Sam（依赖无障碍能力的用户）

- 正面基础包括导航标签、`aria-current`、语义表格和普遍存在的 `aria-label`。
- 10–11px 文本对低视力和 200% 缩放用户构成持续负担。
- hover `title` 不是可靠的键盘、触屏或读屏解释方式。
- Admin 表格最小宽度 920px，窄屏和放大模式下会产生高扫描成本。

## Jordan（首次使用者）

- 首次引导很强，但引导结束后立刻出现 Plan、API Key、RPM、TPM、callback URL、CCS 等术语。
- Key 无法创建时，操作位置缺少明确、持续可见的原因和修复路径。
- Dashboard 优先显示基础设施指标，没有优先回答“我现在是否可以使用、被什么阻塞”。

# Minor Observations

- Accounts 和 Keys 缺少 Dashboard/Admin 那样明确的页面标题与副标题。
- 通知正文被强制单行截断，可能隐藏真正需要采取行动的信息。
- 空状态文案不错，但纠正 CTA 通常在上方工具栏，而不是空状态内部。
- 移动端底部导航和 bottom-sheet 弹窗处理得较好；但 Plan 标签只是压缩到 10px，并未真正降低任务复杂度。
- Dashboard 强调总量和性能，却没有同等强调最紧急的额度风险和访问阻塞。

# Questions to Consider

1. Dashboard 的首要对象是否应该从 Token 总量改成 Account → Plan → Members → Access Key 的协作就绪链？
2. Accounts 和 API Keys 应继续作为同级目的地，还是成为“连接 Codex”任务下的实现细节？
3. 如果 Plan Overview 只能回答一个问题，是否应该是“所有人现在都能使用这个 Plan 吗？不能的话为什么？”
4. 10–11px 字体真的在提升效率，还是在替过多的同时信息买单？
