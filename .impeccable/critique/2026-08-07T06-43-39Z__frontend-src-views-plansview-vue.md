## Design Specificity Verdict

该流程明显为 ShareSub 创作：一次性邀请、固定/共享额度、独立 API Key 和房主控制共同构成产品特有逻辑，并非可替换到任意团队 SaaS 的通用邀请流。主要缺口不是“缺少视觉特色”，而是系统为了追求快速，把受邀者的知情同意和加入后的真实可用性一起自动化掉了。

独立设计审查得出 23/40；detector 对 `frontend/src` 扫描为 0 findings。自动检测没有发现通用反模式，但源码核验发现流程级问题。浏览器与 overlay 按用户和 AGENTS.md 的明确禁令跳过。

## Overall Impression

房主侧“生成并发送链接”很顺，受邀者侧“确认自己将以哪个账号、按什么条件加入”却几乎不存在。最大的机会是增加一个真正的邀请确认页，把身份、Plan、房主、额度方式、份额和有效期一次说清，再由用户主动加入。

## What's Working

- 创建前明确说明链接 7 天有效、仅可领取一次，并警告任何持链且登录的人均可领取。
- 创建、复制、撤销、领取、失败重试、切换账号都有对应反馈；事务锁确保链接只被消费一次。
- 房主能在邀请记录中查看状态和期限，并撤销 pending 邀请；领取后双方都有通知。

## Priority Issues

### [P1] 有效邀请在确认身份和条件前自动领取

**Why it matters:** 已登录用户打开链接，或未登录用户刚完成登录/注册，系统都会立即消费一次性邀请。若当前账号不对，用户没有领取前切换账号的机会；而预览又没有展示接口已返回的 `allocation_mode`、`share_basis_points` 和 `expires_at`。

**Fix:** 增加领取确认步骤，展示“你将以 X 身份加入”、Plan、房主、额度方式、份额、有效期，并提供“确认加入 / 切换账号 / 放弃”。

**Suggested command:** `$impeccable shape`

### [P1] 未绑定账号的 Plan 加入后被送进不可完成的 API Key 向导

**Why it matters:** 接受邀请成功后无条件打开 Key 向导，但该向导只显示可路由 Plan；未绑定账号的 Plan 会被过滤，用户看到空列表和禁用操作，与“接下来配置 API Key”的成功提示矛盾。

**Fix:** 复用现有申请获批路径的可路由判断。可路由时打开 Key 向导；不可路由时进入 Plan 详情并解释“房主绑定账号后才能配置 Key”。

**Suggested command:** `$impeccable harden`

### [P2] 房主创建邀请时看不到剩余可分配份额

**Why it matters:** 后端把活跃成员、未过期 pending 邀请和公开席位预留共同计入 100%。前端份额控件仍允许选择 0–100%，只有提交后才知道超配，默认 10% 在剩余不足时也会直接失败。

**Fix:** 在弹窗展示已用、待领取预留、公开席位预留和剩余份额；把选择器上限限制为剩余份额。0% 应继续保留，因为后端明确支持“仅查看 Plan”。

**Suggested command:** `$impeccable clarify`

### [P2] 多条邀请记录难以对应具体受邀者

**Why it matters:** 每条记录都叫“一次性邀请链接”。链接关闭后不能再次取得，列表也没有房主自定义备注；即使接受后接口返回 `accepted_by_user_id`，界面仍不展示领取人。房主要靠外部聊天记录记忆哪个链接发给了谁。

**Fix:** 在不改变现有接口契约的前提下，先展示 accepted 邀请的领取人信息（若当前 Plan 数据已有可对应成员）；若要支持创建时备注，需先和人类确认业务并设计真实后端字段，不能前端臆造。

**Suggested command:** `$impeccable shape`

### [P2] 移动端和键盘操作丢失关键信息或边界

**Why it matters:** 640px 以下邀请记录直接隐藏份额字段；ModalShell 又设置 `trap-focus=false`，键盘焦点可能逃到遮罩后的页面。移动房主无法核对邀请占用份额，键盘用户也难以判断当前交互范围。

**Fix:** 移动端把份额改为带标签的第二行，不要隐藏；恢复弹窗焦点陷阱并验证关闭后焦点归还触发按钮。

**Suggested command:** `$impeccable audit`

## Persona Red Flags

- **首次受邀者：** 只看到 Plan 名与房主，看不到固定/共享方式、份额和到期时间；登录动作同时变成不可逆的加入动作。
- **Plan 房主：** 不知道当前邀请最多还能分多少；多个匿名链接并列，关闭唯一链接后难以再确认发给了谁。
- **已登录的回访用户：** 浏览器里保留的账号会被直接用于领取；如果不是预期账号，发现时链接已经失效。

## Minor Observations

- 创建成功弹窗应更明确说明：完整链接只在此刻显示，关闭后不能从邀请记录重新复制。
- 领取失败把过期、撤销、已领取等状态合并为一个解释，安全上合理，但可提供不泄漏敏感信息的状态文案层级。
- 邀请流程目前缺少创建、复制、撤销、自动领取、失败恢复和加入后编排的专项测试。

## Questions to Consider

- 快速自动加入是否真的比一次明确确认更重要，尤其链接只能使用一次？
- 对受邀者而言，加入前最少必须知道的是份额、额度模式、房主和期限，还是还要包括账号是否已绑定？
- 房主需要的是“匿名一次性链接”，还是“能记住发给谁的一次性链接”？后者会改变后端数据模型，需要业务确认。
